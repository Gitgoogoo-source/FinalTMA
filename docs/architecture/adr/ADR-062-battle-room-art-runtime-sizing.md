# ADR-062：Battle 首页战场卡片运行时美术尺寸

## 状态

已接受。

## 背景

Battle 首页三个战场卡片分别读取 `/assets/battle/rooms/battle-room-20.webp`、`battle-room-100.webp` 和 `battle-room-500.webp`。三张既有文件均为 1200×560 WebP，合计 469,838 字节；卡片仍按手机端最大 430 CSS px 应用壳、页面左右各 14 px、卡片 2 px 边框和左侧三分之二图片列渲染，因此最大实际图片盒约为 265×118 CSS px。常见 393 CSS px iPhone 上的图片盒约为 241×118 CSS px。

项目 iPhone 验收基线使用 3 倍屏幕像素。最大手机图片盒需要约 796×354 源像素，既有 1200×560 文件超过当前手机运行时清晰显示所需尺寸，并增加 Battle 首次进入时的下载、解码与内存成本。

## 裁决

三张 Battle 首页战场卡片运行时美术统一为不透明 800×373 WebP。该尺寸覆盖最大 430 CSS px 手机壳的 3 倍屏幕像素，同时保留原文件约 15:7 的完整构图和现有 `background-position: center`、`background-size: cover` 裁切语义。现有公开 URL、卡片三分之二布局、卡片高度、选中状态、档位映射和用户可见画面不变。

正式文件只从当前项目正式美术确定性缩小，不重新生成画面，不裁切有效像素，不拉伸，不锐化，也不改变色彩、角色或场景。处理固定使用项目 Sharp 0.35.3、Lanczos3 缩放、WebP quality 82、effort 6、smartSubsample，并移除非必要元数据。

资源门禁固定校验三张文件均为有效 WebP、精确 800×373、没有 Alpha 通道且单张不超过 80 KiB；生产构建复制件必须与 `apps/web/public` 源文件哈希一致。任一规格不满足时停止发布，不能通过放宽尺寸或字节上限绕过。

## 一致性与失败处理

本裁决只改变静态文件尺寸和编码，不改变 Battle 八种页面状态、队伍选择、金额、匹配、战斗、奖励、API、数据库或服务端裁决。缩放必须先在独立临时目录完成，并在覆盖正式文件前逐张验证 MIME、宽高、Alpha、可解码性和完整构图；任一输出失败时不得覆盖原文件。

构建成功只能证明资源格式、复制和代码引用完整，不能代替真实 Telegram 视觉验收。部署后必须在真实 iPhone Telegram Mini App 中检查三张战场卡片的清晰度、中心裁切、角色完整性和切换状态；出现肉眼可见的模糊、色带或异常裁切时，恢复上一 Git 版本并重新按真实显示盒裁决尺寸，不能用 CSS 滤镜掩盖问题。

## 结果

三张正式资源合计降为 217,286 字节，较原 469,838 字节减少 252,552 字节（53.75%）。手机端维持 3 倍屏幕像素覆盖，页面布局和用户可见内容不变。
