# ADR-061：开盒充值继续操作的运行期边界

## 决定

开盒余额不足后创建的 K-coin 充值订单只允许在创建该订单的当前 TMA Web 运行期内恢复一次开盒确认界面。前端在运行内存中把开盒 intent 与服务端返回的唯一充值订单 ID 绑定；只有 `delivered` 订单 ID、订单 intent 和当前内存绑定三者一致时，才生成开盒页 `resume` 参数。刷新、关闭、重新认证、会话敏感状态清理或 Mini App 重新启动都会清除该绑定。新运行期不得仅凭 `topup.bootstrap` 返回的历史 `delivered` 订单打开“确认开盒”弹窗，也不得从历史 `gacha.open` operation 恢复确认或结果展示。

支付订单中的 intent、对应 `topup.create_order` operation、支付状态、K-coin 交付、账本和已完成开盒 operation 继续作为服务端金额校验、付款幂等、资产裁决与审计事实保存。它们不表示存在一笔尚待用户关闭或继续的开盒操作，不具有跨 TMA 运行期的前端展示权限。重新进入后，页面直接使用 `identity.summary`、`gacha.bootstrap`、inventory 与统一权威游标回正真实资产、资格、保底和藏品；用户需要再次从开盒首页主动选择并提交新的 `gacha.open`。

市场购买、幸运转盘、Battle 创建、随机匹配和接受的充值后确认恢复不受本 ADR 改变，继续遵守各自产品契约。该差异由开盒的纯运行期表现规则决定，不扩展为删除支付审计、重复开盒、自动扣款或自动发奖。

## 原因

历史 `delivered` 充值订单是已经完成的付款事实，不是未关闭的前端操作。用模块级已处理集合去重只在单个 JavaScript 运行期有效；TMA 重新启动后集合为空，旧订单会被再次解释为新恢复动作。把展示资格绑定到当前运行内存中的具体订单 ID，可以保留同一支付流程内的继续确认体验，同时从事实模型上阻断历史订单、旧 URL 和已完成开盒记录跨运行期重新弹窗。
